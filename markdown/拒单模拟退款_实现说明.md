# 拒单模拟退款实现说明

日期：2026-10-27。

本轮基于你已修正状态判断的最新代码实现。生产代码只修改 `OrderServiceImpl.reject(OrdersRejectionDTO)`，包括该方法的事务注解和说明；复用现有 Mapper 查询及更新 SQL。

## 一、拒单时如何处理退款

| 订单原状态 | 支付状态 | 处理结果 |
|---|---|---|
| 待接单 `status=2` | 已支付 `pay_status=1` | 模拟模式下改为已取消 `status=6`、已退款 `pay_status=2` |
| 待接单 `status=2` | 未支付 `pay_status=0` | 改为已取消 `status=6`，仍为未支付 `pay_status=0`，不产生退款 |
| 非待接单、订单不存在或支付状态异常 | 任意 | 返回业务错误，不修改订单 |
| 已拒单后再次拒单 | 已取消/已退款 | 不再满足待接单条件，拒绝重复处理，不重复退款或覆盖第一次记录 |

模拟退款表示在本地订单中标记全额退款完成，不调用微信退款接口、不产生真实资金变动。原订单金额保留，不写成 0，也不修改原支付时间。

## 二、方法内的执行顺序

1. 校验 DTO、订单 ID 和拒单原因，拒单原因去掉首尾空格后保存。
2. 根据 ID 查询订单；不存在时抛出业务异常。
3. 复用 `getByIdAndUserIdForUpdate` 加行锁，参数取订单本身的用户 ID，不能使用当前管理员 ID。加锁后再次检查订单必须处于待接单状态，保留你已修正判断的业务含义，并避免空状态导致空指针。
4. 读取 `pay_status`。若为已支付，检查服务端模拟模式已开启，且订单金额为正、支付方式为微信，然后将目标支付状态设为 `Orders.REFUND`。未支付订单的支付状态保持 `Orders.UN_PAID`。
5. 构造只包含拒单相关字段的 `Orders` 更新对象，调用现有 `orderMapper.update`。
6. 拒单状态与模拟退款状态通过同一条 UPDATE、同一事务一起提交。更新失败时回滚，不会留下已拒单但未退款或反过来的半完成结果。

核心更新字段：

```java
Orders update = Orders.builder()
        .id(orders.getId())
        .status(Orders.CANCELLED)
        .payStatus(paid ? Orders.REFUND : Orders.UN_PAID)
        .rejectionReason(ordersRejectionDTO.getRejectionReason().trim())
        .cancelTime(LocalDateTime.now())
        .build();
orderMapper.update(update);
```

方法新增 `@Transactional(rollbackFor = Exception.class)`，复用项目已有事务配置。

| 数据库字段 | 拒单后 |
|---|---|
| `orders.status` | `6`，已取消 |
| `orders.pay_status` | 原已支付则为 `2`；原未支付则保持 `0` |
| `orders.rejection_reason` | 本次填写的拒单原因 |
| `orders.cancel_time` | 本次拒单取消时间 |
| `orders.amount` | 保留原金额 |
| `orders.checkout_time` | 保留原结账时间 |
| `orders.pay_method` | 保留原支付方式 |
| 订单明细、购物车 | 不在拒单方法中修改 |

当前开发配置 `sky.payment.mock-enabled=true` 保持原值。关闭模拟模式后，已支付订单不能在此方法中被伪装成退款成功，会返回明确的业务错误；未支付订单拒单不需要退款，仍可完成。
